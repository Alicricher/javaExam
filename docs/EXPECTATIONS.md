# Ожидания и ограничения

## Что система должна делать

- Студент учится и сдает задания через Telegram-бота.
- Админ управляет системой через web UI.
- Учебный контент должен быть легко создавать, редактировать и удалять.
- Результаты тестов и ситуационных заданий должны удобно фильтроваться.
- Большие списки не должны загружаться целиком.
- Все большие таблицы должны использовать серверную пагинацию.

## Что система не должна делать

- Не должно быть Telegram-админки.
- Админ не должен менять регистрационные поля студента, кроме ФИО.
- Frontend не должен загружать тысячи студентов, тестов или ответов одним запросом.
- Файловые операции не должны позволять выходить за пределы `materialsPath`.
- Импорт вопросов не должен частично записывать некорректную строку.

## Язык интерфейса

Админский интерфейс должен быть на узбекском языке.

Техническая документация может быть на русском, потому что она предназначена для разработки и сопровождения.

## Производительность

Критичные места:

- список студентов;
- результаты тестов;
- ситуационные ответы;
- вопросы тестов;
- история результатов конкретного студента.

Для этих мест ожидаются:

- `page`;
- `size`;
- `total`;
- фильтры на backend;
- отсутствие загрузки всего справочника без необходимости.

## Безопасность

Текущая модель web admin основана на одном пароле. Это допустимо для MVP, но для production желательно:

- отдельные admin users;
- audit log действий;
- CSRF/role hardening;
- ограничение попыток входа;
- ротация пароля;
- HTTPS.

## Известные технические долги

- Bundle frontend большой из-за Ant Design и отсутствия code splitting.
- Нужны интеграционные тесты с реальной PostgreSQL.
- Нужны E2E-тесты основных сценариев админки.
- Для повторной сдачи желательно выбирать тест/задание через UI, а не вводить ID.
- Для AI-проверки желательно логировать модель и версию prompt.
